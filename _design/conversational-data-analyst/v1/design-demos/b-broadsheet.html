Cannot be answered from this data

          

            

              Asked: "Which customers are likely to default next quarter?"

            
There is no credit-risk data in the connected schema.

            
The question asks for a forecast. Halcyon reports what is recorded in
              four tables; it does not predict, and none of them hold arrears, defaults or credit scores.
              The nearest field is customers.risk_band, a static classification set at
              onboarding - using it as a default predictor would be wrong, so it has not been used.

            

              
              
              
            

          

        


        

          
Blocked before execution

          

            

              Asked: "Delete all rejected applications from 2025."

            
This would change the data. Halcyon cannot write.

            
The planner produced a statement beginning DELETE.
              The validator rejected it before it reached the database, and the connection's role holds no
              write grant in any case. Two independent controls, both of which held.

            

              
Rejected statement - never executed

              
DELETE FROM onboarding_applications
WHERE decision = 'rejected'
  AND submitted_at >= DATE '2025-01-01';

              

                
Read-only (SELECT)Statement verb is DELETE. Write verbs are not permitted.

                
Role granthalcyon_ro holds SELECT only - the write would have failed at the database too.

              

            

          

        

      

      

        

          
What Halcyon can answer

          

            
Counts, sums, rankings, rates and trends over
              four tables - customers, branches, onboarding applications and transactions.

            
It will not forecast, infer causes, or reach outside the schema. When a
              question needs data that is not there, it says so rather than approximating.

              Asked: "Show every transaction for all customers since 2019 with running balances."

            
The query was valid, but too heavy to finish.

            
It passed all five safety checks and began executing, then hit the
              five-second statement timeout while scanning 2,914,330 rows in
              transactions with a window function over the whole table. Nothing was left
              running. No partial result is shown, because a partial answer to a question about totals
              is worse than no answer.

Why this happened

          

            
Running balances need a window function over every
              row in range. Six years of transactions is 2.9m rows, and the window cannot use the index.

            
The five-second cap is deliberate: it protects the shared read replica from a
              single expensive question.
